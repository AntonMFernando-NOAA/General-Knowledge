# Chapter 1.3 — Setting Up an Experiment: Rocoto vs ecFlow

> *How the same GFS forecast system bootstraps itself differently depending on
> whether it's running under a research developer or NCO operations — and how
> to trace where every directory comes from in each case.*

The global-workflow can run under two workflow managers: **Rocoto** (used for
development and CI on Hera, Hercules, etc.) and **ecFlow** (used for production
at NCO on WCOSS2). The science is identical. The directory conventions, config
management, and launch procedures are different. This chapter maps them side by
side so the same person can understand both.

---

## 1. The big picture

```
Rocoto path (research/development)
───────────────────────────────────
  User runs setup scripts
        │
        ▼
  EXPDIR/<PSLOT>/          ← experiment config (config.base, config.*, workflow XML)
        │
        ▼
  ROTDIR/<RUN>.YYYYMMDD/HH/ ← all model output and COM data
        │
        ▼
  STMP/RUNDIRS/<PSLOT>/.../ ← per-job working directories (created + deleted at run time)
        │
        ▼
  cron → rocotorun → qsub/sbatch

ecFlow path (operations / dev-ops on WCOSS2)
───────────────────────────────────────────
  Package installed at PACKAGEHOME
        │
        ▼
  ecFlow server holds suite in memory
        │
        ▼
  compath.py → /lfs/h1/ops/prod/com/gfs/v17.0/  ← COM/ROTDIR equivalent
        │
        ▼
  prod_envir sets DATAROOT per-job            ← working directory
        │
        ▼
  ecflow_server → qsub (PBS)
```

The most important conceptual difference: **Rocoto experiments are self-
contained per slot (PSLOT)**; everything a developer needs lives under two
directories (EXPDIR and ROTDIR) that they created and own. **ecFlow production
suites have no user-owned experiment directory**; configuration lives inside
the installed package, and output paths are resolved at runtime from the
operational `compath.py` utility.

---

## 2. Setting up a Rocoto experiment

### Step 1: choose a PSLOT

`PSLOT` is the experiment name — a short tag like `myexpt` or
`c96test_20260604`. Everything else is stamped with it. Pick something that
means something later in a directory listing.

### Step 2: create the experiment

The one-shot script is `dev/workflow/create_experiment.py`. It takes a YAML
configuration file describing the experiment and calls two sub-scripts:

```bash
cd ${HOMEglobal}/dev/workflow
python create_experiment.py -y /path/to/my_case.yaml
```

The YAML file looks like:

```yaml
experiment:
  net: gfs
  mode: cycled
  pslot: myexpt
  idate: 2026060400
  edate: 2026060412
  expdir: /scratch3/NCEPDEV/global/${USER}/RUNTESTS/EXPDIR
  comroot: /scratch3/NCEPDEV/global/${USER}/RUNTESTS/COMROT

workflow:
  engine: rocoto
  rocoto:
    maxtries: 2
    cyclethrottle: 3
```

Under the hood, this calls two scripts in sequence:

1. `setup_expt.py` — creates directories, copies config files.
2. `setup_workflow.py` — generates the Rocoto XML and the crontab entry.

You can also call them manually:

```bash
# Step 1: set up the experiment directory
python setup_expt.py gfs cycled \
    --pslot myexpt \
    --idate 2026060400 \
    --edate 2026060412 \
    --expdir /scratch3/NCEPDEV/global/${USER}/RUNTESTS/EXPDIR \
    --comroot /scratch3/NCEPDEV/global/${USER}/RUNTESTS/COMROT

# Step 2: generate the XML
python setup_workflow.py \
    /scratch3/NCEPDEV/global/${USER}/RUNTESTS/EXPDIR/myexpt \
    rocoto
```

### Step 3: what gets created

After setup, the experiment directory tree looks like:

```
EXPDIR/myexpt/
├── config.base        ← main config (PSLOT, SDATE, EDATE, paths)
├── config.anal        ← analysis options
├── config.fcst        ← forecast options
├── config.com         ← COM path templates
├── config.*           ← one file per major job category
├── myexpt.xml         ← the Rocoto workflow (auto-generated by setup_workflow.py)
├── myexpt.crontab     ← the crontab entry to add
└── myexpt.db          ← created by rocotorun on first run
```

And the COM/output directory skeleton:

```
ROTDIR/
└── gfs.YYYYMMDD/
    └── HH/
        ├── model/
        │   ├── atmos/
        │   │   ├── history/     ← model history files
        │   │   ├── restart/     ← restart files
        │   │   └── input/       ← ICs and BCs
        │   ├── ocean/
        │   ├── wave/
        │   └── ice/
        └── analysis/
            ├── atmos/           ← analysis files
            ├── ocean/
            └── ...
```

`ROTDIR` is the Rocoto equivalent of `compath.py`'s output in production — the
single root under which all model output lives, organized by run and cycle.

### Step 4: where each directory actually lives

Paths are set in two places:

**CLI arguments** (what you pass to `setup_expt.py`):

| Argument | Variable | What it is |
|---|---|---|
| `--expdir` | `EXPDIR` | Root where experiment config dirs live |
| `--comroot` | `COMROOT` | Root where model output dirs live |

**Host-specific defaults** (in `dev/workflow/hosts/<machine>.yaml`, e.g. `ursa.yaml`):

| Variable | Typical Hera value | What it is |
|---|---|---|
| `STMP` | `/scratch4/NCEPDEV/stmp/${USER}` | Fast scratch; job working dirs live here |
| `PTMP` | same as STMP | Parallel scratch (same on most platforms) |
| `HOMEDIR` | `/scratch3/NCEPDEV/global/${USER}` | User's project space |
| `DMPDIR` | `/scratch3/NCEPDEV/global/role.glopara/dump` | Observation dump input |
| `BASE_IC` | `.../data/ICSDIR` | Initial condition files |

**Derived at run time** (inside each job script, not stored in config):

| Variable | Pattern |
|---|---|
| `DATAROOT` | `${STMP}/RUNDIRS/${PSLOT}/${RUN}.YYYYMMDDHH` |
| `DATA` | `${DATAROOT}/<job-specific-subdir>` |
| `COM_*` | Expanded from `COM_*_TMPL` templates at each job start |

`DATAROOT` is the per-job working directory. The job creates it, runs inside
it, and (unless `KEEPDATA=YES`) deletes it when done.

### Step 5: launch

Add the crontab entry:

```bash
crontab -e
# paste the contents of EXPDIR/myexpt/myexpt.crontab
```

That schedules `rocotorun` every five minutes. You can also run it manually at
any time:

```bash
rocotorun -d ${EXPDIR}/myexpt/myexpt.db \
          -w ${EXPDIR}/myexpt/myexpt.xml
```

Check status:

```bash
rocotostat -d ${EXPDIR}/myexpt/myexpt.db \
           -w ${EXPDIR}/myexpt/myexpt.xml
```

### Step 6: logs

Rocoto task logs land inside ROTDIR:

```
ROTDIR/gfs.YYYYMMDD/HH/logs/
└── gfs.tHHz.atmos.prep.log     ← job stdout/stderr for each task
```

Rocoto's own log (submission, state changes) is the `.db` file, but you can
redirect it to a text file:

```bash
rocotorun ... >> ~/logs/myexpt_rocoto.log 2>&1
```

## 3. Setting up an ecFlow experiment (WCOSS2)

ecFlow production doesn't have an "experiment setup" in the same sense.
Instead of each user creating their own experiment directory with config files,
the whole suite is embedded inside a **package** installed at a fixed path, and
the `.def` file references everything relative to `PACKAGEHOME`.

### What PACKAGEHOME is

```
PACKAGEHOME = /lfs/h3/emc/eib/noscrub/%EMC_USER%/gfs/para/packages/gfs.%gfs_ver%
```

That's the root of the installed GFS package. Under it live:

```
packages/gfs.v17.0/
├── ecf/
│   ├── defs/
│   │   └── gfs_prod.def    ← the suite definition
│   ├── scripts/            ← the .ecf task scripts
│   └── include/            ← head.h, tail.h, envir-p1.h
├── jobs/                   ← J-scripts (JGLOBAL_FORECAST etc.)
├── parm/                   ← config files
├── fix/                    ← static data files
├── ush/                    ← utility scripts
└── versions/
    └── run.ver             ← module version pinning
```

So where Rocoto users each have their own EXPDIR, ecFlow ops has one shared
package that everyone's tasks run from. Configuration is baked into that
package and the `edit` variables at the top of the `.def` file.

### The key `.def` variables

At the top of `gfs_prod.def`:

```
suite gfs_v17_nco
  family primary
    edit PACKAGEHOME '/lfs/h3/emc/eib/noscrub/%EMC_USER%/gfs/para/packages/gfs.%gfs_ver%'
    edit NET         'gfs'
    edit RUN         'gfs'
    edit PROJ        'GFS'
    edit PROJENVIR   'DEV'
    edit ENVIR       'prod'
    edit QUEUE       'devhigh'
    edit OUTPUTDIR   '/lfs/h3/emc/eib/noscrub/ptmp/%EMC_USER%/ecflow_gfs/para/output/prod/today'
    family 00
      edit ECF_FILES '%PACKAGEHOME%/ecf/scripts'
```

| Variable | Rocoto equivalent | What it controls |
|---|---|---|
| `PACKAGEHOME` | `HOMEglobal` (repo checkout) | Root of the code and scripts |
| `ECF_FILES` | N/A (scripts embedded in XML `<command>`) | Where ecFlow finds `.ecf` task scripts |
| `OUTPUTDIR` | `ROTDIR/.../logs/` | Job stdout/stderr |
| `ENVIR` | `RUN_ENVIR` | Switches ops vs dev code paths in J-scripts |
| `QUEUE` | `PARTITION_BATCH` (in host YAML) | HPC queue |
| `NET` / `RUN` | Same variables in `config.base` | Model and run identification |

### COM paths (ROTDIR equivalent)

There is no `ROTDIR` variable in the ecFlow `.def` file. COM paths are
resolved at job runtime using `compath.py`:

```bash
ROTDIR=$(compath.py "${envir}/${NET}/${gfs_ver}")
# → /lfs/h1/ops/prod/com/gfs/v17.0
```

The per-cycle path follows the same pattern as Rocoto:

```
/lfs/h1/ops/prod/com/gfs/v17.0/gfs.YYYYMMDD/HH/
```

### DATAROOT (working directory)

In production, the `prod_envir` module sets `DATAROOT` automatically:

```
DATAROOT = /lfs/h2/emc/stmp/<USER>/tmpnwprd/<jobname>.<jobid>
```

In a dev ecFlow setup (like the C96 suite), `prod_envir` is not available
so you set `DATAROOT` yourself, typically under your noscrub space:

```bash
ecflow_client --alter add variable DATAROOT \
    /lfs/h2/emc/global/noscrub/${USER}/c96_run/tmp /gfs_c96
```

The `bootstrap.sh` script under `dev/ecf/c96/` does this automatically.

### No experiment config directory

The biggest thing missing from the ecFlow side, from a Rocoto user's
perspective, is that there's no EXPDIR. You don't create one. The `.def`
file is the config. To change a parameter you either:

- Edit the `.def` file and reload (for permanent changes).
- Use `ecflow_client --alter change variable` (for temporary runtime changes
  without touching the file).

## 4. Side-by-side summary

| Concept | Rocoto (dev) | ecFlow (ops / WCOSS2) |
|---|---|---|
| **Code root** | `HOMEglobal` = repo checkout | `PACKAGEHOME` = installed package |
| **Experiment config** | `EXPDIR/<PSLOT>/` (one dir per experiment) | Embedded in package; suite-level `edit` variables in `.def` |
| **Setup tool** | `create_experiment.py` or `setup_expt.py` | None; edit the `.def` file and reload |
| **COM / model output root** | `ROTDIR` = `COMROOT/<PSLOT>/` | `compath.py` → `/lfs/h1/ops/prod/com/gfs/v17.0/` |
| **Per-cycle COM subdir** | `ROTDIR/<RUN>.YYYYMMDD/HH/` | Same pattern via `compath.py` |
| **Job working dir** | `STMP/RUNDIRS/<PSLOT>/<RUN>.YYYYMMDDHH/` (= `DATAROOT`) | Set by `prod_envir` module; dev: manual `--alter` |
| **Config management** | Config files in `EXPDIR` (`config.base`, `config.*`) | Suite `edit` variables in `.def`, rendered into jobs via `%VAR%` |
| **Workflow definition** | `EXPDIR/<PSLOT>/<PSLOT>.xml` (generated by `setup_workflow.py`) | `ecf/defs/gfs_prod.def` (checked in with the package) |
| **Task scripts** | Inline `<command>` in XML (the J-script path) | `.ecf` files under `ECF_FILES`; each expands `%VAR%` and calls a J-script |
| **Logs** | `ROTDIR/logs/<YYYYMMDDHH>/<task>.log` | Job stdout → `OUTPUTDIR`; PBS `.o<jobid>` in submit dir |
| **Engine startup** | Add crontab entry; cron invokes `rocotorun` every 5 min | Start `ecflow_server` (persistent daemon); `ecflow_client --begin` |
| **Check status** | `rocotostat` | `ecflow_client --get_state` or `ecflow_ui` |
| **Requeue/retry a task** | `rocotorewind` then `rocotoboot` | `ecflow_client --requeue=force` |
| **Update a config value** | Edit `EXPDIR/<PSLOT>/config.*`, re-run `setup_workflow.py` | `ecflow_client --alter change variable` on the running suite |

## 5. How the C96 dev-ecFlow suite fits in

The C96 suite under `dev/ecf/c96/` is a hybrid: it uses ecFlow as the
workflow engine (like production), but it runs from a developer's repo
checkout (like Rocoto). So it borrows conventions from both:

- **PACKAGEHOME / HOMEgfs**: the repo checkout at
  `/lfs/h2/emc/global/noscrub/${USER}/global-workflow_gfsv17`.
  The `.def` file sets `edit PACKAGEHOME '%HOMEgfs%'`.
- **ECF_FILES**: `%HOMEgfs%/dev/ecf/c96/scripts` — task scripts inside the repo,
  not an installed package.
- **DATAROOT**: set by `dev/ecf/c96/bootstrap.sh` to
  `/lfs/h2/emc/global/noscrub/${USER}/c96_run/tmp` — a dev-owned path,
  not the ops `prod_envir` path.
- **COMROOT**: set by `bootstrap.sh` to
  `/lfs/h2/emc/global/noscrub/${USER}/c96_run/com`.
- **LOGROOT**: set by `bootstrap.sh` to
  `/lfs/h2/emc/global/noscrub/${USER}/c96_run/logs`.

The `bootstrap.sh` script is the C96 suite's equivalent of `setup_expt.py`:
it creates the missing directories and applies all the suite-level variable
overrides. Run it once after loading the suite, before `--begin`.

## 6. Mental model to lock in

- **Rocoto**: every experiment is an island. You set it up, it owns its
  directories, it runs on cron. Independent of any other experiment.
- **ecFlow (production)**: there is one global suite running on one server.
  Output paths come from a central registry (`compath.py`). Config lives
  inside the package, not in a per-user directory.
- **ecFlow (dev/C96)**: a hybrid — runs under ecFlow, but the package is
  your repo checkout and the output paths are your noscrub space. `bootstrap.sh`
  fills the role that `setup_expt.py` fills on the Rocoto side.
- **ROTDIR** (Rocoto) ≈ **`compath.py` output** (ecFlow): both are the root
  under which `<RUN>.YYYYMMDD/HH/` cycle directories live.
- **EXPDIR** (Rocoto) has no ecFlow equivalent in production; in the C96 dev
  suite, the `.def` file and `bootstrap.sh` together play the same role.
- **STMP/RUNDIRS/...** (Rocoto DATAROOT) ≈ **`prod_envir` DATAROOT** (ecFlow
  ops) ≈ **`c96_run/tmp/...`** (ecFlow dev): all are the job's scratch working
  directory, created at job start and cleaned up after.
